# 用語集

このリポジトリで働く全エージェントが従う、語の定義。**新しい語を使う前にここを見る。**

---

## この用語集に載せる語・載せない語

判断の基準は1つ。

> **その語を一般的な意味のまま使ったら、この組織では間違った行動になるか。**
>
> **なる → 載せる。ならない → 載せない。**

「べき等」「トランザクション」「リファクタリング」のような一般的な技術用語は載せない。読み手は既に正しく理解しており、載せても何も買えないうえに、毎回読む量だけが増える。

載せるのは3種類。

| 分類 | 何か |
| --- | --- |
| **1. 一般的な意味と違う語** | 誰でも知っている語だが、この組織が意味を狭めた／変えたもの |
| **2. 範囲を明示しないと曖昧になる語** | 指す対象が2つ以上あり、文脈だけでは決まらないもの |
| **3. このプロジェクトの語** | このプロジェクトの外では通じないもの |

**1が最も危険で、最も見落とされる。** 見慣れない語が出てくれば人は調べるが、「テスト」では調べない。知っているつもりでいるからである。**一般語であることが、狭められている事実を隠す。**

## 誰が保守するか

**オーケストレーター。** 層2（組織自身への指示）にあたるため。

新しい語を登録するのは、次のいずれかが起きたとき。

- 設計エージェントが設計成果物で**新しい語を定義した**（機能名、データ構造の名前、ドメインの概念）
- 同じ語について、**2人以上の担当エージェントが違う前提で動いた**
- PO の回答が、ある語の意味を確定させた

担当エージェントは、自分が新しい語を作った場合、**完了報告で申告する。** 登録はオーケストレーターが行う。

**語の定義を変えたら、その語を使っている設計成果物とタスクも直す。** 定義だけ変えて放置すると、古い文書が別の意味で読まれる。

# 1. 一般的な意味と違う語

**この節の語は、一般的な意味のまま使うと規約違反になる。**

## テスト

一般的には検証作業全般を指すが、**この組織では書く主体が分担で決まっている。**

| | 実装エージェント | テストエージェント |
| --- | --- | --- |
| 書くもの | **自分が書いたコードの単体テストだけ** | 結合テスト、シナリオテスト、回帰テスト |
| 視点 | 実装したものが意図どおり動くか | **仕様**に対して満たしているか（第三者の視点） |

「必要なテストを書く」を一般的な意味で受け取ると、実装エージェントが結合テストまで書いてしまう。**一般常識としては正しいが、この組織の規約に反する。**

テストエージェントが単体テストの不足に気づいたら、自分で書かず実装エージェントへ差し戻す。

## 受け入れテスト

**完了条件を、実行できる形にしたもの。** テストエージェントが実装より先に書く。

**書いた時点では落ちているのが正しい。** 一般的な「テストは通るもの」という感覚と逆になる。実装前に通ってしまうなら、テストが完了条件を検証できていないか、既に実装済みかのどちらかであり、オーケストレーターへ報告する。

## レビュー

一般的な「レビュー」に合格基準は無い。**この組織では決まっている。**

| 重大度 | 意味 | 扱い |
| --- | --- | --- |
| **Blocker** | 完了条件を満たさない／明らかなバグ／セキュリティ上の問題 | 修正必須。残っている限り通過させない |
| **Major** | 設計との食い違い／保守性の重大な問題 | 修正必須。別タスクに切り出す相談はできる |
| **Minor** | 改善提案。動作にも保守性にも実害がないもの | 任意。残っていても通過する |

**通過の条件は Blocker と Major が0件。**「だいたい良さそう」で通してはいけない。

レビューエージェントは**自分では直さない。** 修正は実装エージェントの担当である。

## 完了

**完了条件を全て満たし、かつ証拠（実行したコマンドとその実際の出力）が記録されている状態。**

一般的な「終わった」より厳しい。**証拠が無いものは完了ではない。**

## 完了条件

**コマンドを実行して出力を見れば、満たしたかどうかが二値で判定できる形で書かれたもの。**

「使いやすくなっていること」のような主観的な記述は完了条件として成立しない。書かれていないタスクは着手前に差し戻す。

## エスカレーション

**自分で決められないことを上へ渡すこと。4段階と、各段の打ち切り条件が決まっている**（手順は `.claude/rules/org-escalation.md`）。

**段1（自分で解決する）の打ち切りは、時間ではなく「情報源を尽くしたか」で決める。** 作業指示・参照すべき成果物・既存コード・確定済みの決定記録を見ても答えが一つに定まらないなら、それ以上は推測になる。

## 停滞

**2種類ある。単独で「停滞」と書かない。**

| | 実時間基準 | サイクル基準 |
| --- | --- | --- |
| 捉えるもの | セッションをまたいで**放置された**タスク | 1セッション内で**空回りしている**タスク |
| 判定 | 索引の更新日が **2日以上前**、かつ完了でも中止でもない | 往復が**上限（2往復）に達した**、または手戻り回数が3以上 |

**PO確認待ちのタスクは停滞に数えない。** 組織側の停滞ではないため。

## 手戻り

**一度先の工程へ進んだタスクが、前の工程へ差し戻されること。数える対象が決まっている。**

| 数える | 数えない |
| --- | --- |
| レビューからの修正要求 | 実装エージェントが自分で気づいて直したもの |
| テストからの不具合レポート | Minor への対応 |
| オーケストレーターによる担当の差し戻し | |

## 設計

**2種類に分かれ、別のタスクになる。**

| | 方式設計 | 詳細設計 |
| --- | --- | --- |
| 実施時期 | ゴール受領直後 | 各機能の実装直前 |
| 決めること | 全体構成、技術選定、主要なデータ構造、機能間の境界 | API仕様、処理フロー、画面遷移、個別のデータ項目 |
| 完了条件 | 実装タスクへ分割できる状態 | 実装エージェントが判断に迷わず着手できる状態 |

## commit（コミット）

**論理的なまとまり単位で作る。1つのタスクが複数のコミットになってよい。** まとまりができた時点で作り、タスク完了まで溜めない。

## push（プッシュ）

**タスク完了時に行う。レビュー通過を待たない。**

一般的には「レビューを通してから共有する」運用も多いが、この組織では逆である。セッションが途中で切れることを前提に置いているため、ローカルにしか存在しない状態を長く保つと、実装が失われて新しいセッションが続きから拾えなくなる。

## 優先度

**`高` / `中` / `低` の3つだけ。** タスク索引の列に入る値であり、自由記述ではない。

## 依存

**2つの形式があり、書き分ける。**

| 書き方 | 意味 |
| --- | --- |
| `T-001（ブロッカー）` | T-001 が完了するまで、このタスクを開始できない |
| `T-001（推奨: 理由）` | 必須ではないが、この順で進める方が合理的 |
| `無し` | 依存がないことを**確認済み**である |

**ブロッカー指定には理由を必ず書く。理由が書かれていない依存は、依存として認めない。** 説明できない依存は、並行して走れるはずのタスクを不要に直列化する。

# 2. 範囲を明示しないと曖昧になる語

## ユーザー

| 指すもの | 書き方 |
| --- | --- |
| 人間のプロジェクトオーナー | **PO** と書く |
| 開発対象アプリを使う人 | 「アプリの利用者」「エンドユーザー」と書く |

## ドキュメント

**単独で使わない。** このリポジトリには2種類ある。

| | 組織自身への指示 | 成果物の説明 |
| --- | --- | --- |
| 例 | `CLAUDE.md`、`.claude/rules/`、この用語集 | README、API文書、利用者向け仕様 |
| 保守 | **オーケストレーター** | **ドキュメントエージェント** |
| 例文 | 「このリポジトリでは pnpm を使う」 | 「この API はこう呼ぶ」 |

**設計成果物はどちらでもない**（下記）。

## 品質基準

**2種類あり、置き場所が違う。**

| | プロジェクト全体の品質基準 | タスク固有の基準 |
| --- | --- | --- |
| 置き場所 | `CLAUDE.md` / `.claude/rules/` | タスク別ファイルの `## 完了条件` |
| 定める主体 | 設計エージェントが方式設計時に定め、オーケストレーターが書く | オーケストレーター |

**タスクごとに全体の基準を複写しない。** 基準を変えるときに全タスクを直すことになる。

## エージェント

**総称。オーケストレーターを含む6つ全部を指す。** 5つだけを指したいときは「担当エージェント」と書く。

# 3. このプロジェクトの語

## 組織の語

### PO（プロジェクトオーナー）

**人間のユーザー。** ゴールと判断を提供する立場であり、細かな作業指示は出さない。**この組織の中で、PO だけが人間である。**

**PO と直接やりとりできるのはオーケストレーターだけ。** これは方針ではなく技術的な制約による。担当エージェントの「PO に聞きたい」は、必ずオーケストレーターを経由する。

### オーケストレーター

**組織全体を管理・調整する司令塔。このメインセッション自身。** 誰が・何を・どの順番で行うかを判断する。

自分では成果物を作らない。コーディング、テスト実装、通常のドキュメント作成、通常のコードレビューは担当しない。

### 担当エージェント

**オーケストレーターからタスクを割り当てられて実行する側。** 設計・実装・レビュー・テスト・ドキュメントの5つ。

「担当」はタスク索引の列名でもあり、そこに入る値がこの5つのいずれか、または `未割当` である。

### ロール

**責務の単位。ロールは責務の単位であって、知識の単位ではない。** 「セキュリティに詳しいエージェントが欲しい」の多くは、レビューロールにスキルを足せば済む。

## 記録の語

### タスク台帳

**進捗についての唯一の真実。2つのファイルに分かれている**（書き方は `.claude/rules/org-task-ledger.md`）。

| ファイル | 役割 | 誰が書くか |
| --- | --- | --- |
| `docs/task-list-{プロジェクト名}.csv` | **索引** | **オーケストレーターだけ** |
| `docs/tasks/T-XXX.md` | **タスク別の詳細** | 担当エージェント（自分のタスクの分だけ） |

**タスク別ファイルは、そのまま作業指示である。** 作業指示を別途書き下ろさない。項目が空であることが、指示の抜けを目に見える形にする。

### 決定ログ / 作業ログ / 証拠

タスク別ファイルの中にある、**性質の違う3つの記録**。混ぜない。

| 名前 | 答えるもの | 寿命 |
| --- | --- | --- |
| **決定ログ** | **なぜそうしたか** | 恒久。過去の項目を書き換えず、上書きする新項目を足す |
| **作業ログ** | 何が、どの順で起きたか | 一時的。完了時に数行へ畳む |
| **証拠** | 完了条件を満たしたと何故言えるか。コマンドとその実際の出力だけ | 恒久 |

### PO確認待ちキュー

`docs/po-queue.md`。**PO の判断を仰いでいる質問の一覧。** 1件を `Q-001` のような番号で識別する。

### 引き継ぎ記録

`docs/handover.md`。**「今どこにいるか」を1枚に書いたもの。** 常に上書きし、過去分は Git の履歴に残す。

### 設計成果物

**設計エージェントが書く、組織の内側に向けた文書。** 何をどう作るか、そして**なぜその方式にしたか、どの案を却下したか**を記録する。

利用者向けの文書とは読み手が違う。設計成果物は「なぜそうしたか」、利用者向け文書は「現在どうなっているか、どう使うか」。

### エージェント用マスタ / 人間用ビュー

利用者向け文書は2階建てになっている。

| | エージェント用マスタ | 人間用ビュー |
| --- | --- | --- |
| 位置づけ | **正典。ここだけが真実** | マスタからの**生成物** |
| 更新 | ドキュメントエージェントが直接書く | **スクリプトで生成する。手で書かない** |

## 進め方の語

### TDD適用可否

**そのタスクで、テストを実装より先に書くかどうか。** TDD（テスト駆動開発 — 先に失敗するテストを書き、それを通すように実装する進め方）は既定である。

事前にテストを書けないタスク（探索的な調査、見た目の調整、設定変更など）は「適用外」と明示する。**判定するのはオーケストレーター。**

### 反復上限（2往復）

**レビューや不具合修正の往復は2回で打ち切る。**「レビュー → 修正 → 再レビュー」で1往復。

2往復して解決しないなら、指摘の伝わり方か、設計・要件の側に構造的な問題がある。**往復が収束しないこと自体が、判定基準（完了条件や設計）の不備を示す信号。**

### ゴール健全性評価

**組織が最終ゴールへ近づいているかの判定。** タスクの消化数だけを見ない。判定は3つ。

| 判定 | 目安 |
| --- | --- |
| **前進している** | 完了数が増え、かつ**残作業が減っている** |
| **停滞している** | 完了数が増えていない。停滞やブロックが積み上がっている |
| **ゴールが揺らいでいる** | 完了数は増えているのに、**残作業が減っていない、または増えている** |

## プロジェクトルート

`.media-agent/` を含むディレクトリ。`-C` 指定が無ければカレントディレクトリから上方へ探索して決まる（6.3）。

**「リポジトリのルート」と取り違えないこと。** Media Agent 本体のリポジトリではなく、
**Media Agent を導入した利用者側のディレクトリ**を指す。この2つを混同すると、
Core が本体リポジトリの構造に依存し、開発原則6（Project固有情報をCoreに混ぜない）が壊れる。

出所: 方式設計 6.3 / 7章

## スタブコマンド

Stage 0 では未実装であることを標準エラーへ明示し、**終了コード 10** で終わる CLI コマンド。
Stage 0 では `setup` / `post` / `research` / `analyze` の4つ（6.4）。

**「何もしないコマンド」と取ると、終了コード 0 で実装してしまう。**
成功と区別できることが要件である。スクリプトや CI から呼ばれたときに、
未実装が成功として通過してはならない。

出所: 方式設計 6.4

## スキャフォールド（scaffold）

`media-agent init` が `.media-agent/` 配下の初期ファイル群を生成する処理。

**汎用的なコード生成器ではない。** 対象は `.media-agent/` 配下だけであり、
利用者のプロジェクトの他のファイルには触れない。

出所: 方式設計 7章

## 組み込み Agent（builtin agent）

Media Agent 本体に同梱される検証用の Agent。**Stage 0 では AI を呼ばない。**

**Content Agent 等の本番 Agent と取り違えないこと。** Stage 0 の組み込み Agent は、
Agent Runtime が動くことを示すためだけに存在する。

出所: 方式設計 5.1

## AgentRegistry / AgentRunner

Agent の登録簿（Registry）と、登録された Agent を Task として実行する実行器（Runner）。
Custom Agent も同じ Registry へ合流する。

**Registry を「設定ファイル」と取り違えないこと。** 実行時のオブジェクト登録簿である。

出所: 方式設計 5章 / 9.2

## PolicyDecision

Policy Engine の判定結果。`outcome`（`allow` / `require_approval` / `deny`）と
`reason_code`（`mode_auto` / `mode_approval` / `mode_disabled` / `limit_exceeded` 等）の**2要素**を持つ。

**`deny` と `limit_exceeded` を同じ値にしないこと。** そうすると受け入れテスト S-G の
「許可 / 承認が必要 / 禁止 / 上限超過」の4通りを区別できない。
**結果の種類（outcome）と理由（reason_code）は別の軸である。**

出所: 方式設計 19章 / 詳細は T-002

## 運用ログ / 監査記録（Logger / Audit）

**別物である。** 運用ログは人間が動作を追うためのログ（`logs/media-agent.log`）。
監査記録は AI の判断を追跡する追記専用の記録（`logs/audit.jsonl` と DB の Decision）。

**両者を「ログ」と一括りにすると、片方だけ実装される。**
別々に実装することが T-002・T-005 の完了条件である。
根拠は要件定義書5.5節・20.3節（可観測性）・20.5節（再現性）。

出所: 方式設計 5.1 / 7章

## 拡張点（Extension Point）

Stage 1 以降の機能を足す位置として、Stage 0 が**予約しておく場所**。

**「実装済みの拡張機構」と取り違えないこと。** ディレクトリすら作らない拡張点がある
（例: `connectors/`）。予約とは「そこに足せる設計になっている」という意味であって、
足す仕組みが動いているという意味ではない。

出所: 方式設計 13章

## 終了コード表

CLI の異常がすべて落ちる先の対応表（0 / 1 / 2 / 3 / 4 / 5 / 6 / 10 / 70）。
例外は `media_agent.errors.MediaAgentError` を基底とし、**クラス属性として自分の終了コードを持つ**。
**変換は CLI 層だけで行う。**

**「非ゼロならなんでもよい」と取らないこと。** そう扱うと、受け入れテストが終了コードではなく
メッセージ文字列を判定するようになり、文面を変えるたびにテストが壊れる。

出所: 方式設計 6.5

## ProjectLayout

`.media-agent/` 配下のパスを1つのオブジェクトへまとめた解決結果。
`core/` はこれか個別の `Path` を**引数で受け取る**（4.1）。

**「ディレクトリ構造の説明」と取らないこと。** そう取ると Core が自分でパスを組み立ててしまい、
品質基準 Q7（`core/` が Project 固有の事情を持たない）が壊れる。

出所: 詳細設計 4.1

## AuditRecorder

監査記録の**唯一の書き込み口**。`decisions` テーブルと `audit.jsonl` の両方へ、この順で書く（11.3）。

**「ログの一種」と取らないこと。** そう取ると `logging` へ流す実装になり、
`logging.level` の設定で監査記録が消せてしまう。監査は消せてはならない。

出所: 詳細設計 11.3

## check id

`doctor` の各検査に付けた安定した識別子（`structure.files` 等、15個）。
**出力に必ず現れ、テストはこれを判定する。**

**「表示名」と取って文言と一緒に変えないこと。** 受け入れテストが壊れる。
**文言は変えてよいが、id は契約である。**

出所: 詳細設計 13.2

## 安定文字列

受け入れテストが `in` で判定してよい文字列。**これ以外の文言は実装が自由に変えてよい。**

**「エラーメッセージ全文」を判定対象と取らないこと。** そう取ると、文面を改善するたびにテストが落ちる。

出所: 詳細設計 3章 / 17.3

## ローリングウィンドウ（上限判定の窓）

Policy の上限判定で使う、判定時刻からさかのぼる固定長の時間窓（`per_day` = 24時間、`per_hour` = 1時間）。

**「1日」をカレンダー日（0時区切り）と取らないこと。** そう取るとタイムゾーンの扱いが必要になり、
判定結果が実行時刻で変わる。

出所: 詳細設計 10.5

## 代理計数（Stage 0 の上限計数）

Action の実行回数の代わりに、**`allow` と判定した回数**を数えること。
Stage 0 には Action の実行先が存在しないため。

**「実行回数を数えている」と取らないこと。** そう取ると、Stage 3 で Action を実装したときに二重計上する。
**Stage 3 で差し替えが必要である。**

出所: 詳細設計 10.5 / D-X1

## スキーマ版数（`SCHEMA_VERSION` / `config.version`）

DB の構造版数（`PRAGMA user_version`）と、設定ファイルの構造版数。
**互いに独立であり、パッケージ版数とも独立である。**

**どれか1つを「バージョン」と総称しないこと。** 総称すると、コードだけ直したいときにも
設定の移行が要るように見える。

**2026-08-24 追記: 3軸目がある。** `audit.jsonl` の各行が持つ `schema_version`
（`AUDIT_SCHEMA_VERSION`、現在 1）。DB の構造版数とも config の構造版数とも独立である。

出所: 詳細設計 7章 / T-005（`6deb006`）

## 未実装の枠（`not_implemented_yet` / 終了コード 70）

**「Stage 0 で実装すると決まっているが、その実装タスクがまだ来ていない」状態**を表す枠。
`src/media_agent/cli/commands/_pending.py` の `not_implemented_yet()` が `NotImplementedError` を投げ、
CLI 層が終了コード **70** へ変換する。

**スタブコマンド（終了コード 10）と混同しないこと。** 別の概念である。

| | 意味 | 終了コード | Stage 0 の最終形 |
| --- | --- | --- | --- |
| **スタブコマンド** | Stage 0 では**実装しない**と決めたコマンド（`setup` / `post` / `research` / `analyze`） | 10 | このまま残る |
| **未実装の枠** | Stage 0 で実装するが、担当タスクが未着手 | 70 | **全て置き換えられて消える** |

**Stage 0 の完了時点で 70 が返るコマンドが残っていたら、それは置き換え漏れである。**
区別してあるのは、この漏れを終了コードだけで検出できるようにするため。

出所: T-004 決定ログ

## CliContext

CLI のグローバルオプションの値と、そこから導かれるプロジェクト解決・Config 読み込みの入口
（`src/media_agent/cli/context.py`）。

**Click の `Context` とは別物である。** 同じ「コンテキスト」でも、Click のものは
コマンド呼び出しの状態を持つフレームワーク側の型であり、`CliContext` はこのプロジェクトが
その上に載せた解決結果である。

出所: T-004 決定ログ

## ProjectPaths

`core/` が DB の置き場所を**構造的に**受け取るための Protocol（`db_path` だけを要求する）。
`ProjectLayout` はこれを構造的に満たすため、呼び出し側は設計どおり `ProjectLayout` を渡せる。

**「ProjectLayout の別名」と取らないこと。** 別名として扱うと `core/` から `project/` を
import することになり、**品質基準 Q7（`core/` が Project 固有の事情を持たない）が壊れる。**
2つが別に存在するのは、その静的依存を作らないためだけである。

出所: T-005 決定ログ / 方式設計 5.2
