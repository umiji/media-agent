## 確定すべき3件

### D-1（RV-1・Major・最優先）構造が壊れたプロジェクトでの期待値

**詳細設計 17.2「コマンド × 状況の一覧」は4状況しか定めていない。** 次の状況の期待値が無い。

- `.media-agent/data/media-agent.db` が SQLite ファイルでない
- `.media-agent/logs/` が通常ファイルである
- `.media-agent/data/` が通常ファイルである

**現状の実測（T-009 が確認）**: `status` / `run` / `task list` / **`init`** が終了コード **70「内部エラー」**になる。
`sqlite3.DatabaseError` / `OSError` が `media_agent.errors` の階層へ包まれず素通りしている
（`src/media_agent/core/db/connection.py:51-52`、`src/media_agent/project/scaffold.py:129,187`）。

**実害**: `doctor` は同じ状況を終了コード 5 で正確に診断し `media-agent init を実行してください` と助言する。
**その助言に従うと 70 で終わる。利用者から見て復旧経路が行き止まりになっている。**

決めること:

1. 各コマンド（`init` / `doctor` / `status` / `run` / `agent list` / `task list`）が返すべき終了コード
2. 使うべき例外型（`media_agent.errors` の既存の型か、新設か）
3. 利用者へ出すべきメッセージと Hint（**行き止まりにしないこと**）
4. `doctor` が終了コード 5 で診断することとの整合

**同じ DB 由来でも、スキーマ版数の不一致は `DatabaseVersionError` として正しく包まれ終了コード 1 になる。
扱いの非対称を、意図的なものにするのか揃えるのかを決めること。**

### D-2（RV-3）`Agent.version` の永続化の要否

**`Agent.version` がどこにも永続化されない。** `decisions` にも `tasks` にも列が無く、`AuditRecord` にも項目が無い。
用途は `agent list` / `status` の表示だけ（`src/media_agent/cli/rendering.py:99`）。

**要件定義書 20.5 は「同じ Input・設定・Agent Version から実行内容を追跡可能とする」と定めており、
詳細設計 8.1 も `version` を 20.5 の手段と説明している。** 記録側に受け皿が無い。

決めること:

1. Stage 0 で永続化するか、Stage 1 以降へ送るか（**送るなら、要件20.5 を Stage 0 では一部しか満たさないことを明示的に受け入れる判断として記録すること**）
2. 永続化する場合の格納先（`decisions` の列か、`AuditRecord` の項目か、両方か）
3. Migration 版数 2 と `AUDIT_SCHEMA_VERSION` の扱い

**Stage 0 には利用者が存在せず、移行すべき既存データが無い。** 後から足すほど高くつく類の変更である。
**その事実を判断材料に含めること。**

### D-3（RV-6）`task list --limit` の値域

`--status` は値域を検査して `UsageError`（終了コード 2）にするが、`--limit` には下限検査が無い
（`src/media_agent/cli/commands/task.py:33-36`）。`--limit -1` は SQLite の `LIMIT -1`（無制限）になり、
`--limit 0` は行があるのに `(タスクはありません)` と出る。**詳細設計 16.2 に定めが無い。**

決めること: `--limit` の値域と、範囲外の扱い（終了コード）。**`--status` との扱いを揃えるか否か。**

## 決定ログ

### 2026-08-25 D-1 構造破損は終了コード 1 で終わり、`doctor` の助言と一致させる

- 決定: `.media-agent/` 配下の構造破損（種別1: ディレクトリであるべきパスが通常ファイル／種別2: DB が SQLite として開けない）を
  **`ProjectStructureError`（新設・終了コード 1）** と **`DatabaseError`（既存・終了コード 1）** で表す。`init` / `status` / `run` / `task list` は 1、
  `doctor` は 5、`agent list` は 0。`sqlite3.Error` / `OSError` を CLI 層まで通さない（終了コード 70 を出さない）。
  **`doctor` の hint（検査2・7・10）を「退避してから `media-agent init`」に変え、助言どおりに実行すれば復旧するようにした**（17.4.4 の4手順）
- 決定: **どのコマンドも壊れた対象を退避・削除・上書きしない。** 退避の主語は利用者である（17.4 の R-2）
- 決定: DB 由来の異常は、版数不一致（`DatabaseVersionError`）も中身の破損も**同じ終了コード 1** に揃えた（T-009 が指摘した非対称の解消）
- 却下案:
  - **A 構造破損に新しい終了コード（例 7）を割り当てる** → 終了コード表は方式設計 6.5 の持ち物であり、本タスクの変更範囲外
  - **B `doctor` と同じ 5 にする** → 5 は `DoctorCheckFailedError` に固定されている。`status` が 5 を返すと「doctor が落ちた」と読める
  - **C 未初期化（3）として扱う** → `.media-agent/` は現に存在する。事実に反する
  - **D `init` が壊れた対象を自動で退避して作り直す** → 12.5 の「利用者のファイルに触らない」を破る
  - **E degrade して続行（`logs/` が使えなければ stderr だけへ出す）** → `run` が監査記録を残せないまま判断する（11.3・品質基準 Q9/Q10）
  - **F `UsageError`（2）にする** → 使い方の誤りではなく環境の異常。`-C` の指定ミスと区別できなくなる
- 付帯条件: `.media-agent/` 自体が通常ファイルの場合は**既存どおり**（`init` は `ScaffoldError`、他は 3）。12.5 で確定済みの判断を蒸し返さない。
  安定文字列と終了コードが同じため、受け入れテストからは区別できない
- 出典: `docs/design/stage0-detail.md` 17.2 / 17.4。実測は本ファイルの `## 証拠`

### 2026-08-25 D-2 `Agent.version` を Stage 0 で永続化する（Migration 版数 2）

- 決定: **Stage 0 で永続化する。** 格納先は `decisions.agent_version`（正本）と `audit.jsonl` のメタ情報キー `agent_version`。
  `SCHEMA_VERSION` を **1 → 2**（`ALTER TABLE decisions ADD COLUMN agent_version INTEGER`）、`AUDIT_SCHEMA_VERSION` を **1 → 2**。
  値は `AgentRunner` が渡す。`kind='policy_check'` の行は `NULL`
- 決定: **要件定義書5.5節の Audit 9項目の対応表は変えない。** `agent_version` はメタ情報として足す。要件との対応が読めなくなるため
- 却下案:
  - **Stage 1 以降へ送る** → 要件20.5 を Stage 0 では一部しか満たさない状態が続き、後から足すと利用者 DB の移行が必要になる。
    **Stage 0 には移行対象の利用者データが1件も無く、今が最も安い**（タスク指示が判断材料に含めることを求めた事実）
  - **版数1の DDL に列を直接足す（`SCHEMA_VERSION` は 1 のまま）** → 7.1 の「前進のみの連番」を破る。既存の版数1の DB は列を欠いたまま
    「版数1」を自称するため、`doctor` は合格を出すのに実行時に 70 になる。**D-1 で潰したばかりの失敗の形**
  - **`tasks` にも列を持たせる** → 同じ事実が2か所に書かれる
  - **`AuditRecord` と JSONL にだけ持たせ、DB 列を作らない** → 正本（DB）から辿れない
  - **`AUDIT_SCHEMA_VERSION` を 1 のまま据え置く** → 「古い行にキーが無い」のか「値が無かった」のかを読み手が判別できない
- 付帯条件: 追加のみの `ALTER TABLE` であり既存行を書き換えないため、共通の停止条件 S-2 には当たらない（本タスクの停止条件を明示的に判定した）。
  **既存の受け入れテスト2件（`test_stage0_audit.py:64` / `test_stage0_lifecycle_sequence.py:104`）がリテラル `1` を期待しており、T-013 が定数比較へ直す必要がある**
- 出典: `docs/design/stage0-detail.md` 6.4 / 7.1 / 7.3 / 11.3 / 19.1

### 2026-08-25 D-3 `--limit` は 1 以上。範囲外は `UsageError`（終了コード 2）

- 決定: `--limit` の値域を **1 以上の整数**とし、`0` 以下は `click.UsageError`（終了コード 2）。**上限は設けない。**
  検査は `--status` と**同じ場所**（プロジェクトを開いた後）で行い、両方が不正なら `--status` を先に報告する
- 却下案:
  - **`click.IntRange(min=1)`** → 検査が型変換の段で起き、未初期化ディレクトリでも 2 が返って 17.2 の1行目と食い違う
  - **`--limit 0` を「0件表示」として許す** → 行があるのに `(タスクはありません)` と出る（RV-6 の実測）
  - **負値を「無制限」として許す** → SQLite の `LIMIT -1` という実装詳細が CLI の仕様になる
  - **上限（例 1000）を設ける** → Stage 0 に根拠となる件数が無い
  - **`--status` 側を `Choice` へ寄せて揃える** → 通っている判定を作り直すことになり、変更範囲を超える
- 出典: `docs/design/stage0-detail.md` 16.2
