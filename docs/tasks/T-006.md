## 目的

Media Agent の中核である「Agent を実行し、Task として管理し、Action の前に Policy で制御する」構造を作る。

要件定義書2.4節「DecisionとActionを分離」と開発原則5・8の実体がここである。
**Stage 0 の時点で Action の実行先（X 等）は存在しないが、Policy Check の関門を先に作っておくことに意味がある。**
後から差し込む構造にすると、Action を実装した時点で関門を通らない経路が残る。

## 変更範囲

- Agent Interface（要件定義書5.1節）
  - Agent 登録 / 実行 / Input 渡し / Output 取得 / 実行状態管理 / エラー処理 / 実行ログ
  - **検証用のダミー Agent**（T-002 で定義されたもの。実際の AI 呼び出しは行わない）
- Task（要件定義書5.2節）
  - 状態 `pending` / `running` / `completed` / `failed` / `cancelled` と、T-002 が定めた状態遷移の制御
- Policy Engine（要件定義書5.3節・13節）
  - Action ごとの `mode`（`auto` / `approval` / `disabled`）と上限値の判定
- 上記に対応する単体テスト
- 本ファイル `docs/tasks/T-006.md` の 決定ログ / 作業ログ / 証拠 / 進捗

**`doctor` / `status` / `run` の統合は T-007 の範囲。** このタスクは Runtime・Task・Policy を
ライブラリとして完成させるところまでを担当する。

## 完了条件

1. Agent を Runtime へ登録し、Input を渡して実行し、Output を取得できる（**受け入れテスト S-E**）
2. Agent の実行が Task として永続化され、**T-002 が定めた状態遷移どおりに遷移する**（**受け入れテスト S-F**）
   - 正常系: `pending` → `running` → `completed`
   - 異常系: Agent が例外を投げたとき `failed` になり、**例外がそのまま外へ漏れない**
   - T-002 が定義していない遷移が**拒否される**こと
3. Agent の実行が Audit へ記録される（T-005 の Audit を使う。**新しい記録機構を作らない**）
4. Policy Engine が、少なくとも次の4通りを設計どおりに判定する（**受け入れテスト S-G**）
   - 許可（`mode: auto`）
   - 承認が必要（`mode: approval`）
   - 禁止（`mode: disabled`）
   - 上限超過（1日最大投稿数などの上限に達している）
5. Policy の設定が `config.yaml` から読み込まれる（T-004 の Config を使う。**独自に設定を読まない**）
6. Agent がエラーで落ちたとき、要件定義書5.1節「Agentエラー処理」どおりに扱われ、Audit に `error` が残る
7. Custom Agent のロードは**設計のみで実装しない**（要件定義書19節の表で S0 は「設計」）。
   T-002 の設計が実装を要求している場合は、着手前に停止条件として報告する

## 禁止事項

- **受け入れテスト（T-003 が書いたテスト）を書き換えて通さない。** テストが誤っていると判断したら、
  直さずに停止条件として報告する。`.claude/rules/org-task-ledger.md`「やってはいけないこと」に該当する
- 設計成果物（`docs/design/` 配下）を書き換えない。読み方に迷ったら org-design へ問い合わせる（1往復まで）
- `docs/requirements-media-agent-v0.2.md` / `docs/task-list-media-agent.csv` / `docs/handover.md` /
  `docs/po-queue.md` / 他タスクの `docs/tasks/T-XXX.md` を書き換えない
- **X API クライアントを書かない。外部ネットワークへ送信するコードを書かない**（PO 制約 C-1・C-3、
  および要件定義書28節「Stage 0ではまだX APIやニュース取得等を実装しない」）
- **認証情報を必要とする実装をしない。** 認証情報をリポジトリへ置かない（PO 制約 C-2、要件定義書14.2節）
- **Stage 1 以降の機能を実装しない。** Content / Research / Strategy / Analytics / Engagement / Orchestrator の
  各 Agent、Google News / RSS / Web Connector、過去投稿 Import、重複チェック、AI 呼び出しは範囲外
- **本タスクの `変更範囲` の外にあるファイルを変更しない。** 他の実装タスクが担当する領域に不足を見つけても、
  その場で直さずに報告する（`CLAUDE.md`「スコープを勝手に広げない」）
- スコープ外のリファクタリング・警告修正をしない
- **AI（LLM）を呼び出す実装をしない。** Stage 0 では AI 処理の実行方式そのものが未決である（要件定義書24節10番）
- **Policy Check を経由しない Action 実行経路を作らない**（要件定義書2.4節・開発原則5）

## テスト方法

- 単体テスト: Agent 登録・実行、状態遷移の許可/拒否、Policy の各判定、例外処理
- 受け入れテスト: T-003 が書いた S-E / S-F / S-G を実行する
- 実環境確認: **要**。ダミー Agent を実際に実行し、Task と Audit の記録を目視確認する。実施者は担当自身
- 回帰: T-004 / T-005 の受け入れテスト（S-A / S-D / S-H / S-I）が引き続き通ること

## 停止条件

共通の停止条件に加えて:

- T-002 の Task 状態遷移の定義に、到達不能な状態または矛盾がある
- Policy Model の定義だけでは、受け入れテスト S-G の4通りを判定できない
- 実装のために AI 呼び出しまたは外部接続が必要になった
