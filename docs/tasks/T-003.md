## 目的

Stage 0 の完了条件を、**実行可能な受け入れテスト**へ変換する。
この組織は TDD を既定とするため、実装（T-004〜T-007）より先にテストが存在し、**この時点では落ちるのが正しい**。

先に書く理由は、完了条件を後から実装に合わせて緩められないようにするためである。
実装後に書いたテストは、実装の写像になる。

## 変更範囲

- T-001 が定めた Test 構造の配下に、受け入れテストを新規作成する
- テストの実行に必要な最小限の設定ファイル（テスト用の fixture、`conftest.py` 相当）
- 本ファイル `docs/tasks/T-003.md` の 決定ログ / 作業ログ / 証拠 / 進捗

## 禁止事項

- **製品コードを書かない。** テストを通すための実装は T-004〜T-007 の担当である。
  テストが `ImportError` で落ちるからといって、空のモジュールを作って回避しない
- 単体テストを書かない（単体テストは実装エージェントの担当。`docs/glossary.md`「テスト」を参照）
- 設計成果物（`docs/design/` 配下）を書き換えない
- `docs/task-list-media-agent.csv` / `docs/handover.md` / `docs/po-queue.md` / 他タスクの `T-XXX.md` を書き換えない
- **ネットワークへ出るテストを書かない。** Stage 0 に外部接続は存在しない。
  テストが外部へ出るなら、それは設計かテストのどちらかが誤っている
- 認証情報を要求するテストを書かない（PO 制約 C-2）

## 完了条件

以下を全て満たすこと。

1. 受け入れテストが存在し、**T-001 が定めたテスト実行コマンドで収集・実行できる**

   > **重要（T-001 の順序制約 O-2 / `docs/design/stage0-architecture.md` 17.2）**
   > このタスクは T-004 より前に走るため、着手時点で `pyproject.toml` も `media_agent` パッケージも
   > **存在しない**。受け入れテストは収集時に `ModuleNotFoundError` で落ちる。
   > **これが「未実装だから落ちた」証拠として正しい状態である。**
   > 証拠の取り方: `pip install pytest` だけを入れた仮想環境で `pytest tests/acceptance` を実行し、
   > その出力を `## 証拠` へ貼ること。
   > **空のモジュールや `pyproject.toml` を作って収集エラーを回避しないこと**（下記の禁止事項）。
   > 完了条件1 の「収集・実行できる」は、この形で実行できることを指す。
2. 次のシナリオが受け入れテストとして表現されている。これは要件定義書18節 Stage 0 の検証条件そのものである
   - **S-A** 空のディレクトリで `media-agent init` を実行すると `.media-agent/` が生成され、
     設計どおりのファイル（`config.yaml` / `strategy.md` / `rules.md` / `agents/` / `memory/` / `data/` / `logs/`）が揃う
   - **S-B** `init` 済みのプロジェクトで `media-agent doctor` を実行すると、検証項目が全て合格し、
     **終了コード 0** で終わる。**認証情報が無いことを異常として報告しない**
   - **S-C** `init` 済みのプロジェクトで `media-agent status` を実行すると、
     現在の Agent / Task の状態が出力され、終了コード 0 で終わる
   - **S-D** `init` していないディレクトリで `doctor` / `status` を実行すると、
     **明確なエラーメッセージとともに非ゼロの終了コード**で終わる（沈黙して成功しないこと）
3. 次の Core 機能が受け入れテストとして表現されている
   - **S-E** Agent を Runtime へ登録し、Input を渡して実行し、Output を取得できる（設計のダミー Agent を使う）
   - **S-F** Agent 実行が Task として記録され、`pending` → `running` → `completed` の状態遷移が観測できる。
     失敗する Agent を実行すると `failed` になる
   - **S-G** Policy Engine が、設定された `mode`（`auto` / `approval` / `disabled`）と上限値に対して
     設計どおりの判定結果を返す。**少なくとも「許可」「承認が必要」「禁止」「上限超過」の4通り**を確認すること
   - **S-H** Agent の実行が Audit へ記録され、要件定義書5.5節の9項目が追跡できる
   - **S-I** `config.yaml` が壊れている／必須項目が欠けている場合に、**設計どおりのエラーで落ちる**
4. **X API・外部ネットワーク・認証情報を一切使っていない**（実装の禁止事項でもあるが、テスト側でも守ること）
5. **テストを実行し、落ちることを確認して、その実出力を `## 証拠` へ貼っている。**
   「落ちた」という事実と、**落ちた理由が「未実装だから」であること**が読み取れる形で記録すること
6. 各シナリオが、要件定義書のどの節・設計成果物のどの箇所に対応するかが、テスト内のコメントか
   一覧表のどちらかで追える

## 判断してよい範囲

- テストの分割・ファイル構成・命名（T-001 の Test 構造に従う範囲で）
- fixture の作り方、一時ディレクトリの扱い方

- シナリオの期待値のうち、設計成果物に明記がなく、かつ技術的に一意に定まるもの

**上記シナリオを削ることは判断してよい範囲に含まれない。** 削る必要があると判断したら停止条件へ。
