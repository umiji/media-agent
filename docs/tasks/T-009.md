## 完了条件

1. 次の観点で全てレビューし、指摘に **Blocker / Major / Minor** の重大度が付いている
   - **要件との対応** — 要件定義書18節 Stage 0 の実装項目が全て存在するか（Python Package / CLI /
     Project初期化 / `.media-agent/` / Config / DB / Logging / Audit / Task / Agent Interface /
     Policy基盤 / Test基盤）
   - **設計との整合** — 実装が `docs/design/` 配下の設計成果物どおりか。差異があれば、
     設計と実装のどちらを正とすべきかの意見を添える
   - **非機能要件** — 要件定義書20節の6項目（拡張性 / 保守性 / 可観測性 / 安全性 / 再現性 / 移植性）。
     特に **20.2 CoreとProject固有ロジックの分離**（開発原則6）と
     **20.4 DecisionとActionの分離**（開発原則5）は Stage 0 の設計思想の核なので必ず見ること
   - **保守性** — Stage 1 以降で Agent / Connector を追加する際に、Core を書き換えずに済む構造か
   - **明らかなバグ・リスク** — 例外処理の漏れ、ファイル破壊、冪等でない初期化
   - **セキュリティ** — 要件定義書14節。Credential がリポジトリに入っていないか、`.gitignore` が効いているか
2. **PO 制約の遵守を確認している**（ゴール達成条件 A-8）
   - X API クライアント・外部ネットワーク送信のコードが**無い**
   - 認証情報がリポジトリに**無い**
   - Stage 1 以降の機能（Content / Research / Strategy / Analytics / Engagement / Orchestrator、
     Google News / RSS / Web Connector）が実装されて**いない**
   - 確認に使ったコマンドと結果を `## 証拠` へ記録すること
3. **Blocker / Major の指摘が0件である。** 0件でない場合は org-implementation へ修正要求を返す（2往復まで）。
   2往復で収束しなければ、収束していなくてもオーケストレーターへ返す
4. Minor の指摘は、修正するかどうかの判断をオーケストレーターへ委ね、一覧として報告に含める
5. **T-004 が ruff の `select` から E501（行長）を外した判断を確認する。**
   理由は「T-003 のテスト docstring が101件違反し、`ruff format` では解消できず、
   テストの文面書き換えは禁止事項だったため」。**品質基準 Q2 の実効性が下がっていないか**を見ること。
   妥当と判断するなら、その旨を報告に書く（オーケストレーターが層2へ反映する）
6. **T-003 が設計の記述だけでは決まらず自分で決めた期待値 K-1〜K-6 が、設計成果物と矛盾していないかを確認する。**
   一覧は `docs/tasks/T-004.md` の「T-003 からの申し送り」にある。
   TDD では受け入れテストが実装より先に固まるため、テストが設計の穴を独自解釈で埋めた箇所は
   **誰も照合しないまま契約になる。** ここを見るのはレビューだけである
7. `docs/glossary.md` に無い語で、設計・実装が新たに定義した語があれば、報告で申告する（登録はオーケストレーターが行う）
