### 2026-08-23 Config の未知キーを検証エラーにする

- 付帯条件: 認証情報の項目を Config に置かないため、`extra="forbid"` は「認証情報を `config.yaml` へ書けない」ことの担保も兼ねる（18.2 の6）

### 2026-08-23 Migration は `PRAGMA user_version` の前進のみとする
- 決定: 版数を `PRAGMA user_version` に持ち、`(version, description, statements)` の連番一覧をコードに置く。未適用分を1つずつ1トランザクションで適用する（7章）
- 却下案: Alembic → SQLAlchemy が前提で、方式設計 3.4 が ORM を却下済み／独自の `schema_migrations` テーブル → 「テーブルが1つも無い状態」の分岐が最初に要る／`CREATE TABLE IF NOT EXISTS` だけ → 列の追加・変更を表現できず、既存 DB の形を判定できない／`.sql` をパッケージデータ化 → 資源読み込みの罠（T-4）を DB 層にも持ち込む
- 出典: 詳細設計 7.1 / 7.4

### 2026-08-23 Agent Interface は ABC とし、戻り値に `decision` / `reason` を必須で含める
- 決定: `Agent(ABC)` に `name` / `version` / `description` のクラス属性と `run(input, ctx) -> AgentOutput` を置く。`AgentOutput` は `payload` / `decision` / `reason`（8.1）
- 却下案: `typing.Protocol` → 登録時に妥当性を確認できず、属性の欠落が実行時まで判明しない／`dict` を返すだけ → Audit の必須項目（decision / reason）を Runner が推測することになる。**何を判断したかを知っているのは Agent 自身だけである**
- 出典: 詳細設計 8.1

### 2026-08-23 Agent の失敗を Runner が捕捉し、例外を外へ出さない
- 決定: `AgentRunner.run()` は `Exception` を捕捉して Task を `failed` にし、Audit へ `error` を残し、`TaskRunResult` を返す。`BaseException` は捕捉しない（8.3）
- 却下案: 例外を再送出する → 呼び出し側が毎回 try/except を書くことになり、書き忘れた経路で Task が `running` のまま残る
- 出典: 詳細設計 8.3（T-006 完了条件2「例外がそのまま外へ漏れない」）

### 2026-08-23 検証用の組み込み Agent として `echo` と `fail` を同梱する
- 決定: `echo`（入力をそのまま返す）と `fail`（常に例外を送出する）の2つを製品に同梱し、どちらも `agent list` に出す（8.4）
- 却下案: `echo` だけ同梱し、失敗系はテスト側で定義する → T-003 の禁止事項（製品コードを書かない）と、CLI から異常系を観測したいという要求が両立しない
- 付帯条件: `fail` が送出する例外は `MediaAgentError` の階層に**属さない**（`RuntimeError` 派生）。Runner が「Agent が投げた任意の例外」を扱えることを組み込みで検証するため
- 出典: 詳細設計 8.4

### 2026-08-23 Task の `running` → `cancelled` を Stage 0 では禁止する
- 決定: 許す遷移は `pending→running` / `pending→cancelled` / `running→completed` / `running→failed` の4つだけ。表に無い遷移は `InvalidTaskTransitionError` で拒否し、DB を書き換えない（9.2）
- 却下案: `running→cancelled` を許し「中断要求」の意味にする → Stage 0 の Agent 実行は同期呼び出しで中断手段が無い。「`cancelled` と記録されているのに Agent は最後まで動いた」状態を作れてしまう。状態名と実態が食い違う
- 付帯条件: 非同期実行・Scheduler が入る Stage 3 以降で、中断機構と**同時に**解禁する（未解決 D-X3）
- 出典: 詳細設計 9.2

### 2026-08-23 Policy の判定順序を「禁止 → 上限 → 承認」に固定する
- 決定: 9段の評価順（10.4）を定め、最初に該当した規則で確定する。`outcome` 3値 × `reason_code` 9値の値域を確定（10.2）
- 却下案: `require_approval` を先に評価する → 「承認すれば禁止トピックでも投稿できる」設計になり、要件13節の「特定トピック禁止」が骨抜きになる
- 付帯条件: S-G の4通りは `(allow, mode_auto)` / `(require_approval, mode_approval)` / `(deny, mode_disabled)` / `(deny, limit_exceeded_per_day)` で区別する。**「禁止」と「上限超過」は `outcome` が同じで `reason_code` だけが違う**
- 出典: 詳細設計 10.2 / 10.3 / 10.4

### 2026-08-23 上限の窓をローリングウィンドウとし、`allow` 件数を代理計数とする
- 決定: `per_day` = 判定時刻から24時間、`per_hour` = 1時間。数える対象は `decisions` の `kind='policy_check' AND decision='allow'`（10.5）
- 却下案: カレンダー日（0時区切り） → タイムゾーン項目を `config.yaml` に増やすことになり、UTC 固定にすると利用者から見て説明のつかない時刻に上限が切り替わる
- 付帯条件: Stage 0 に Action の実行が無いため、「許可した回数」で代用する。**Stage 3 で Action を実装する際に `count_allowed_actions` を実行回数の計数へ差し替える**（未解決 D-X1）。差し替えないと二重計上になる
- 出典: 詳細設計 10.5 / 22章 D-X1

### 2026-08-23 `PolicyEngine.check()` は既定で判定を記録する
- 決定: `check(request, *, record=True)`。記録は `AuditRecorder` 経由で、その記録が上限計数の入力になる。`record=False` は副作用なしの試算用（10.6）
- 却下案: 純関数にして計数を外部に委ねる → 記録する呼び出しと計数する呼び出しがずれると、上限が永遠に来ない、または二重に消費される
- 出典: 詳細設計 10.6

### 2026-08-23 運用ログと監査記録を機構ごと分ける
- 決定: 11.1 の10観点（目的・出力先・形式・書き込み口・抑制・欠落・回転・トレースバック・秘密値・正本）で別物として定義する。運用ログは `logging` + サイズ回転（1MiB×3）、監査記録は `AuditRecorder` のみを口とし**回転しない**
- 却下案: Audit を運用ログの1レベル（`AUDIT` レベル等）として実装する → `logging.level` の設定で監査記録が消える経路が生まれる。**設定で消せるならそれは監査記録ではない**／Audit も回転させる → 監査記録が消える
- 出典: 詳細設計 11.1 / 11.2

### 2026-08-23 監査記録は DB → JSONL の順に書き、DB を正本とする
- 決定: `decisions` へ INSERT・コミットしてから `audit.jsonl` へ append する。JSONL の失敗は運用ログの ERROR に留め、例外にしない。DB の失敗は例外（11.3）
- 却下案: JSONL を先に書く → DB 側が失敗したとき、Task と結び付かない監査行が残る／どちらか片方だけ書く → JSONL だけでは `status` の集計と上限判定ができず、DB だけでは DB を開けない状況で監査を目視できない

### 2026-08-23 `init` は冪等とし、上書きは `--force` に限定する
