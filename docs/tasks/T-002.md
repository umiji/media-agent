## 目的

T-001 が決めた構造と技術選定の上に、**実装エージェントが判断に迷わず着手できる粒度**の詳細設計を置く。
要件定義書28節「最初に決定する対象」14項目のうち、T-001 が扱わなかった6項目を確定させる。

ここが曖昧だと、T-004〜T-007 の実装が互いに食い違ったモデルを作る。
特に Task / Agent / Policy は3つの実装タスクにまたがるため、境界を先に固定する必要がある。

## 完了条件

以下を全て満たすこと。

1. `docs/design/stage0-detail.md` が存在し、次の6項目に結論がある
   - **Config Schema** — 要件定義書8.2節の `config.yaml` を満たすこと。項目名・型・必須/任意・既定値・
     検証エラー時の挙動を表で示すこと。要件定義書13節の Automation Policy 設定もここに含める
   - **DB Schema** — 要件定義書16節の6 Entity（Project / Source / Post / Performance / Task / Decision）。
     列名・型・NULL可否・主キー・外部キー・インデックスを示すこと。
     **Stage 0 で実際にテーブルを作るのは6 Entity 全てとする**（Stage 1 以降が使う Entity も器だけ先に作る。
     後から Migration を書く手間を避けるため。この判断を採らない場合は理由を決定ログへ書くこと）
   - **Agent Interface** — Agent の登録・実行・Input 受け渡し・Output 取得・状態管理・エラー処理の
     シグネチャ。要件定義書5.1節を満たすこと。Stage 0 では実際の AI 呼び出しを行わないので、
     **検証用のダミー Agent を1つ以上定義すること**（Runtime が動くことを示せる最小の Agent）
   - **Task Model** — 状態は要件定義書5.2節の `pending` / `running` / `completed` / `failed` / `cancelled`。
     **許される状態遷移を図または表で明示すること。** 遷移が書かれていないと実装ごとに解釈が分かれる
   - **Policy Model** — 要件定義書5.3節・13節。Action ごとの `mode`（`auto` / `approval` / `disabled`）と
     上限値（1日最大投稿数・1時間最大Action数など）。**Policy Check の入力と出力の型**を定義すること。
     Stage 0 では Action の実行先が存在しないため、Policy Engine は「判定結果を返すだけ」でよい
   - **Logging / Audit** — 要件定義書5.5節の9項目（timestamp / agent / task / input / decision / reason /
     action / result / error）。出力先・フォーマット・ローテーションの有無。
     **Logger（運用ログ）と Audit（判断の追跡記録）を別物として定義すること**。要件定義書20.3・20.5節が根拠
2. **Migration 方式に結論がある**（要件定義書24節14番）。初回スキーマ作成と、将来のスキーマ変更をどう扱うか
3. 各項目に、実装が判断に迷いうる点の結論が書かれている。具体的には次に答えていること
   - `media-agent init` が生成するファイルの**中身**（`config.yaml` / `strategy.md` / `rules.md` の雛形）
   - 既に `.media-agent/` が存在する場合の `init` の挙動
   - DB ファイルの置き場所（`.media-agent/` 配下のどこか）
   - `doctor` が検証する項目の一覧と、それぞれの合格条件
   - `status` が出力する内容
   - `run` が Stage 0 の時点で何を実行するか（実 Agent が無いため、ダミー Agent を回すのか、何もせず終了するのか）
4. **要件定義書14節（Security）への対応が書かれている。** Credential を Git へコミットしない仕組み
   （`.gitignore` の対象、`doctor` での検証）。**Stage 0 では認証情報を必要とする機能が無いため、
   doctor は「認証情報の不在」を異常として扱わないこと**
5. 決定ログに、複数案があった箇所が却下案つきで記録されている
