- 依存: T-012（ブロッカー）— 期待値が確定していないとテストが書けないため。**この順序を崩すと、テストが独自解釈で期待値を作り、誰にも照合されないまま契約になる**（`docs/handover.md`「TDD の構造上の弱点への対処」）
- TDD適用可否: 適用（実装より先に書き、この時点では落ちるのが正しい）

## 目的

T-012 が確定させた期待値を、**機械で判定できる形**にする。T-014（実装）が通すべき的を先に置く。

## 変更範囲

- `tests/acceptance/` への追加（既存ファイルへの追加でも、新規シナリオでもよい）
- 本ファイル `docs/tasks/T-013.md` の 決定ログ / 作業ログ / 証拠 / 進捗

## 完了条件

1. **T-012 が確定させた D-1 / D-2 / D-3 の期待値が、すべて受け入れテストとして存在する**
2. **新しく書いたテストが落ちている。落ちた理由が「未実装」であり、期待値の不一致でないこと**
   （落ち方を `## 証拠` に記録する。**通ってしまうものがあれば、それは既に満たされているということなので、その旨を明記する**）
3. **既存の 538 件に回帰が無い**（新規追加分を除いて件数と結果が変わらないこと）
4. `ruff check .` / `ruff format --check .` の終了コードが 0
5. `claude/session-resume-mdqrmg` へ push している

## 判断してよい範囲

- テストの粒度・配置・命名
- 構造が壊れたプロジェクトの作り方（fixture の手段）

## 禁止事項

- **製品コード（`src/` 配下）を変更しない**
- **設計成果物（`docs/design/` 配下）を書き換えない。** T-012 の期待値に疑義があれば、
  直さずに停止条件として報告する（org-design へは1往復まで問い合わせてよい）
- **T-012 が定めていない期待値を自分で作らない。** 決まっていないものがあれば報告する。
  **これが T-003 で起きた「独自解釈が契約になる」問題の再発防止である**
- 既存のテストを書き換えない
- **ネットワークへ出るテスト・認証情報を要求するテストを書かない**（PO 制約 C-1・C-2）
- `docs/task-list-media-agent.csv` / `docs/handover.md` / `docs/po-queue.md` / 他タスクの `T-XXX.md` を書き換えない
- **`os.chdir` を使わない**（方式設計 10.3）。やむを得ない場合は `monkeypatch.chdir` を使い、逸脱を docstring に明記する
  （S-J に前例がある。T-009 が妥当と判定済み）

## テスト方法

`PATH="$PWD/.venv/bin:$PATH" .venv/bin/pytest -q` で、**新規分が落ち、既存 538 件が通る**ことを確認する。

- 期待値どおりのテストを書くために製品コードの変更が必要になった
