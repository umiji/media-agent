## 決定ログ

### 2026-08-23 Python の最低バージョンを 3.11 とする
- 決定: `requires-python = ">=3.11"`。CI の検証対象は 3.11 / 3.12 / 3.13
- 却下案: `>=3.9` / `>=3.10` → `tomllib` が無く、得られるのは「古い環境で動く」だけ。利用者は自分の開発機に入れる想定であり該当場面が無い / `>=3.12` `>=3.13` → 実行環境の既定 `python3` が 3.11.15 であり、全コマンドで別インタプリタの明示が必要になる。3.12 以降の固有機能を使う予定も無い
- 出典: `docs/design/stage0-architecture.md` 3.1

### 2026-08-23 CLI Framework に Click を採用する
- 決定: `click>=8.1,<9`。`click.testing.CliRunner` を受け入れテストの CLI 検証手段とする
- 却下案: Typer → 実体は Click のラッパで、テストも終了コード制御も結局 Click 経由。層が1枚増える分だけエラー制御が遠くなる / argparse → `CliRunner` 相当のテストハーネスが無く、10 コマンド分の組み立てと出力捕捉を手書きすることになる。PyYAML が必須依存として残るため「依存ゼロ」も達成できない / Fire・docopt → 引数仕様が暗黙化し `--help` と実挙動の整合を機械的に保てない
- 付帯条件: 上限 `<9` は、9 系で非推奨 API の削除が予告されているため（本タスクで `click.__version__` の非推奨警告を確認）
- 出典: `docs/design/stage0-architecture.md` 3.2

### 2026-08-23 設定は PyYAML（safe_load）で読み、Pydantic v2 で検証する
- 決定: `PyYAML>=6.0` + `pydantic>=2.7,<3`。`yaml.load` は使わない
- 却下案: dataclasses + 手書きバリデータ → 必須・既定値・型変換・エラーメッセージを項目ごとに手書きすることになり、検証エラー時の挙動の一貫性を人手で担保できない / jsonschema → 検証後も型が付かず、スキーマとモデルで真実が2つになる / ruamel.yaml → コメント保持・往復編集は Stage 0 で使わない機能 / TOML へ変更 → 要件定義書8.2節の `config.yaml` と食い違う。要件定義書は PO の持ち物 / python-dotenv → Stage 0 に認証情報を要する機能が無い（PO 制約 C-2）
- 出典: `docs/design/stage0-architecture.md` 3.3

### 2026-08-23 DB は標準ライブラリ sqlite3 + 手書き SQL の Repository 層とする
- 決定: `.media-agent/data/media-agent.db` に SQLite。ORM を使わず Repository 層で SQL を隠す
- 却下案: SQLAlchemy(+Alembic) → 6テーブルに対して抽象化が過大。セッション管理という第二の状態機械が Task の状態遷移と混ざる。Repository を挟めば後から差し替えられる / JSON・CSV 直書き → 検索・インデックス・関連（Post↔Performance）を扱えず Stage 1 の重複チェックで行き詰まる / TinyDB → 依存が増えるだけで SQLite への優位が無い / PostgreSQL・MySQL → サーバと接続情報が必要になり PO 制約 C-2 とローカル完結の前提に反する / DuckDB・ベクトル DB → 要件定義書23節が MVP 非対象と明記
- 付帯条件: 接続ごとに `PRAGMA foreign_keys = ON` を明示すること（SQLite の既定は OFF）。Migration の具体は T-002
- 出典: `docs/design/stage0-architecture.md` 3.4

### 2026-08-23 テストは pytest とし、実行コマンドは `pytest` とする
- 決定: `pytest>=8` + `pytest-cov`。単体テストは `tests/unit/`、受け入れテストは `tests/acceptance/`。カバレッジ閾値は設けない
- 却下案: unittest → `tmp_path` 相当・パラメタライズ・autouse fixture を自前で用意することになり、全テストへのネットワーク遮断も書き忘れを検出できない / nose2 → 保守が止まっている / tox・nox → 複数環境は CI の matrix で足り、ローカルに第二の実行系を作ると正のコマンドが曖昧になる / `--cov-fail-under` の導入 → 骨格実装の段階で数値の根拠が無く、閾値充足のためのテストが書かれると受け入れテストの意味が薄れる
- 出典: `docs/design/stage0-architecture.md` 3.5・10章

### 2026-08-23 リンタ・フォーマッタは Ruff、型チェックは mypy とする
- 決定: `ruff check .` / `ruff format --check .` / `mypy src`。mypy は `--strict` にせず、対象は `src/media_agent` のみ
- 却下案: black+flake8+isort → ツール3つ・設定3つになり相互調整の手間が恒常的に残る / pylint → 既定の指摘が多く骨格実装で抑制コメントを量産する / 型チェックを入れない → Agent Interface・Task・Policy が3つの実装タスクにまたがるため、型の食い違いをコマンドで検出できる価値が大きい / pyright → Node.js 実行環境への依存が増える
- 出典: `docs/design/stage0-architecture.md` 3.6

### 2026-08-23 パッケージは src レイアウト + hatchling とする
- 決定: `src/media_agent/`、ビルドバックエンドは hatchling、開発導入は `pip install -e ".[dev]"`。設定は `pyproject.toml` に集約する
- 却下案: フラットレイアウト → 未インストールでも import でき、entry point の欠陥をテストが見逃す / setuptools → 動作はするが src レイアウトのパッケージ探索とテンプレート同梱に追加設定が要る / Poetry・PDM → 独自のロック運用が加わるが Stage 0 に必要な利得が無い / setuptools-scm → タグの無い作業ブランチで版数が不定になり、版数の単一の真実を `__init__.py` に置く方針と両立しない
- 付帯条件: **ここで決めたのはローカル開発インストールのみ。** PyPI 公開等の「Package 配布方式」は Stage 8 の対象であり決めていない
- 出典: `docs/design/stage0-architecture.md` 3.7・4章

### 2026-08-23 GitHub Actions は「CI のみ」を Stage 0 に置く
- 決定: `.github/workflows/ci.yml`（テストとリントのみ、Secrets 不参照、matrix 3.11/3.12/3.13）を Stage 0 に置く。Scheduler としての定期実行 workflow は置かない
- 却下案: 19節の表（GitHub Actions は S3 以降）を根拠に Stage 0 では一切置かない → 28節13番が「最初に決定する対象」に GitHub Actions を挙げており、T-007 完了条件6 も workflow の存在を求める。両者は対象が違う（19節の行は要件5.6節の Scheduler、28節は決定対象）と解釈し、矛盾ではないと判断した / `main` への push のみでトリガ → 今回の作業は作業ブランチ上で進むため CI が一度も走らない / 単一 Python バージョン → 「>=3.11」の宣言を検証しないまま公言することになる
- 出典: `docs/design/stage0-architecture.md` 11章

### 2026-08-23 Stage 0 の CLI コマンドを実装・スタブへ切り分ける
- 決定: 実装 = `init` / `doctor` / `status` / `run` / `agent list` / `task list`。スタブ = `setup` / `post` / `research` / `analyze`。スタブは標準エラーへ未実装である旨を出し、**終了コード 10** で終わる
- 却下案: `setup` を config.yaml の対話編集として実装 → Connector 設定が入る Stage 3 で作り直しになる / `task` `agent` もスタブにする → Runtime と Task は Stage 0 の実装対象なのに CLI から観測できず、受け入れテストが内部 API を直接叩くことになる / スタブを終了コード 0 で終える → スクリプトや CI から成功と区別できず「沈黙して成功しない」という要求に反する

### 2026-08-23 版数の単一の真実を `__init__.py` に置き、Stage と minor を対応させる
