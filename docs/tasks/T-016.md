## 決定ログ

### 2026-08-25 利用者向け文書に版数の数字を書かない（`N` と伏せ、数字は 1 か所に集める）

- 決定: 出力例に出てくる版数（DB のスキーマ版数・`config.yaml` の構造版数・監査記録の形式版数）を
  すべて `N` と伏せた。**数字を書くのは `docs/features/project-directory.md` の 2 か所だけ**
  （DB の節と監査記録の節）とし、その旨を本文に明記した。
  手順書・CLI リファレンス・クイックスタートには数字を一切書かない。
  **T-013 が受け入れテストで採った解（版数のリテラルは1本だけに置き、他は定数と比較する）の文書版である。**
- 却下案1: 数字を 2 へ書き換えて回る → 版数が上がるたびに全文書が実物と食い違う。今回の食い違いを生んだ構造そのもの。
- 却下案2: 出力例から版数の行ごと削る → `doctor` の出力例は 15 行そろっていることに意味があり、
  行を落とすと「期待される出力」と実物の行数が合わなくなる。
- 却下案3: 生成スクリプトで実装の定数から数字を差し込む → `docs/tools/build_docs.py` の変更が要り、
  本タスクの変更範囲外。またマスタ（エージェントが読む正典）側が置換前の姿になり、マスタの可読性が落ちる。
- 付帯条件: 伏せ字であることが読み手に伝わるよう、**各文書に `N` の説明を置いた**。
  手順書では「数字ではなく `[ok]` であることを見る」と確認項目へ書き、PO が数字の差で異常と誤認しないようにした。
- 出典: セッション内の判断。T-016 の「判断してよい範囲」／T-013 決定ログ

### 2026-08-25 `audit.jsonl` の例を実出力から取り直し、`json` コードフェンスを外した

- 決定: 例に `agent_version` を含め、`input` / `result` を直前の手順で実行するコマンド
  （`run --input '{"note":"hello media agent"}'`）の実出力に合わせた。`schema_version` を `N` にした結果
  JSON として妥当でなくなるため、フェンスを ```` ```json ```` から素のコードブロックへ変えた。
- 却下案: `json` フェンスを保ったまま `schema_version` だけ数字を残す → 版数の数字を1か所に集める決定と矛盾する。
  そもそもこのブロックは可読性のために折り返してあり、既に「そのままの1行」ではない。
- 出典: セッション内の判断（実出力は本ファイル `## 証拠` E-2）
