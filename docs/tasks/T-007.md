## 目的

要件定義書18節 Stage 0 の検証条件
「`media-agent init` → Project生成 → `media-agent doctor` → `media-agent status` が正常動作すること」
を実際に満たす。**このタスクの完了が、今回のゴール達成条件 A-2 の充足である。**

あわせて Test 基盤を仕上げ、GitHub Actions でテストが回る状態にする。
要件定義書28節「最初に決定する対象」の Test構造・GitHub Actions を、設計から実装へ落とす工程である。

## 変更範囲

- `media-agent doctor` の実装（T-002 が定めた検証項目）
- `media-agent status` の実装（T-002 が定めた出力内容）
- `media-agent run` の実装（Stage 0 の時点での挙動は T-002 の設計に従う）
- Test 基盤の仕上げ（T-001 の Test 構造。テスト実行コマンド、カバレッジ設定などがあれば）
- GitHub Actions workflow（`.github/workflows/` 配下。**テストとリントを実行するだけのもの**）
- 上記に対応する単体テスト
- 本ファイル `docs/tasks/T-007.md` の 決定ログ / 作業ログ / 証拠 / 進捗

## 完了条件

1. `media-agent doctor` が T-002 の検証項目を全て実行し、`init` 済みプロジェクトで**終了コード 0** になる
   （**受け入れテスト S-B**）
2. **`doctor` が、認証情報が無いことを異常として報告しない。**
   Stage 0 には認証情報を必要とする機能が存在しないため（PO 制約 C-2、要件定義書14節）
3. `media-agent status` が現在の Agent / Task の状態を出力し、終了コード 0 になる（**受け入れテスト S-C**）
4. `media-agent run` が T-002 の設計どおりに動作する
5. **受け入れテスト S-A 〜 S-I が全て通る。** 落ちているものが1つも無いこと
6. GitHub Actions の workflow が存在し、push で**テストとリントが実行される**構成になっている
   （実際の CI 実行結果の確認までは求めない。workflow ファイルの妥当性まで）
7. 要件定義書17節の Logging / Audit 要件どおり、`run` の実行が追跡可能な形で記録される
8. **リポジトリのルートに、T-001 が定めたコマンドで実際にテストとリントが通る**

### 全実装タスク共通の完了条件

上記に加えて、次を全て満たすこと。

- **自分が書いたコードに単体テストがある**（受け入れテストは T-003 の担当。単体テストは実装の担当）
- T-001 が定めたテスト実行コマンドとリントコマンドが**通る**
- **担当範囲の受け入れテストが通る。** 他タスクの範囲に依存して落ちているものは、
  どのテストがなぜ落ちているかを `## 証拠` に明記して残す（そのまま次タスクへ引き継がれる）
- 論理的なまとまりごとに commit し、**タスク完了時に `claude/mvp01-implementation-testing-0ldwtq` へ push している**
  （レビュー通過を待たない。`CLAUDE.md` の Git 規約）
- `## 証拠` に、テスト実行コマンドと**実出力**、コミット SHA が記録されている

## 禁止事項

- **受け入れテスト（T-003 が書いたテスト）を書き換えて通さない。** テストが誤っていると判断したら、
  直さずに停止条件として報告する。`.claude/rules/org-task-ledger.md`「やってはいけないこと」に該当する
- 設計成果物（`docs/design/` 配下）を書き換えない。読み方に迷ったら org-design へ問い合わせる（1往復まで）
- `docs/requirements-media-agent-v0.2.md` / `docs/task-list-media-agent.csv` / `docs/handover.md` /
  `docs/po-queue.md` / 他タスクの `docs/tasks/T-XXX.md` を書き換えない
- **X API クライアントを書かない。外部ネットワークへ送信するコードを書かない**（PO 制約 C-1・C-3、
  および要件定義書28節「Stage 0ではまだX APIやニュース取得等を実装しない」）
- **認証情報を必要とする実装をしない。** 認証情報をリポジトリへ置かない（PO 制約 C-2、要件定義書14.2節）
- **Stage 1 以降の機能を実装しない。** Content / Research / Strategy / Analytics / Engagement / Orchestrator の
  各 Agent、Google News / RSS / Web Connector、過去投稿 Import、重複チェック、AI 呼び出しは範囲外
- **本タスクの `変更範囲` の外にあるファイルを変更しない。** 他の実装タスクが担当する領域に不足を見つけても、
  その場で直さずに報告する（`CLAUDE.md`「スコープを勝手に広げない」）
- スコープ外のリファクタリング・警告修正をしない
- **GitHub Actions に、外部サービスへ接続する job・認証情報を要求する job を書かない**（PO 制約 C-1・C-2）
- **Scheduler（cron 実行）を実装しない。** 要件定義書19節の表で GitHub Actions は S3 から。
  Stage 0 で作るのは「テストを回す CI」であり、定期実行の仕組みではない

## テスト方法

- 単体テスト: doctor の各検証項目、status の出力生成、run の制御
- 受け入れテスト: T-003 が書いた S-A 〜 S-I を**全て**実行する
- 実環境確認: **要**。一時ディレクトリで `init` → `doctor` → `status` → `run` を実際に順番に実行し、
  実出力を `## 証拠` へ記録する。実施者は担当自身
- 回帰: T-004 / T-005 / T-006 の受け入れテストが引き続き通ること

## 停止条件

共通の停止条件に加えて:

- 受け入れテストのうち、**設計どおりに実装しても通らないもの**がある
- `doctor` の検証項目に、認証情報または外部接続を必須とするものが含まれている
- Stage 0 の範囲で `run` が何をすべきか、T-002 の設計から一意に定まらない
